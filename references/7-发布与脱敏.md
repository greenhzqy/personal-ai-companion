# 发布与脱敏：把「自己」公开出去而不被扒光

> 这一阶段最容易翻车，因为它有一个**反直觉的真相**：
> **你的仓库里最私密的东西，往往不是照片，而是那些看起来像"配置文件"的文件。**

---

## 一、真实事故（照做前先看这一段）

某次准备把一个「桌面 AI 伙伴」项目从私有转公开。当事人的认知是：

> 「代价就是 26 张音乐人照片会公开。」

实际扫描后发现会公开的是：

| 类别 | 具体内容 | 出现在 |
|---|---|---|
| **真名** | 本人全名 | 8 个已跟踪文件（含 `<title>`、署名、作者页） |
| **学籍** | 学校 + 专业 + 年级 | 作者页一行 |
| **私人事务** | 副业交易、待办清单、固定收入来源 | 运行时状态文件 |
| **自省原文** | 每周自问的原始答案 | 同上 |
| **财务渠道** | 本人真实在用的收入渠道名 | 账本下拉选项的硬编码 |
| **目录结构** | 某个**个人资料目录**的绝对路径（含真名） | 服务端常量 |
| **年龄与求职目标** | 年龄、目标岗位 | 提示词常量 |
| **第三方素材** | 音乐人照片 + 歌词文件 | 素材目录 |

而且这些**都已经在历史提交里**——`git rm` 和 `.gitignore` 都救不回来。

> 结论：**发布前必须用脚本全量扫描，不靠印象。** 下面就是那套流程。

---

## 二、第一步：把"会公开什么"分成三类

**A 类 · 有意署名** —— 你本来就打算挂的名（笔名/ID/真名）。
→ 保留，但**逐项确认范围**。「愿意挂真名」不等于「愿意挂学校+专业+年级」。

**B 类 · 你没想到的** —— 运行时数据、私人待办、绝对路径、提交信息。
→ 默认**全部移除**，除非他明确同意。

**C 类 · 第三方的** —— 照片、歌词、字体、图标、数据集。
→ 默认**不打包**，让使用者自备。仓库只放目录结构与清单。

**先问这三个问题，再动手**：
1. 你愿意公开的是**真名**还是**别名**？（两者差别巨大）
2. 学校 / 单位 / 年级 / 城市 要不要挂？
3. 素材（照片/歌词）是你自己的吗？不是你自己的就别进仓库。

---

## 三、第二步：扫描清单与命令

### 按类别准备关键词

| 类别 | 关键词示例 |
|---|---|
| 身份 | 真名、别名、学校全称与简称、单位、年级、年龄、城市 |
| 联系 | 邮箱、手机号、微信号、学号、QQ |
| 路径 | `D:\`、`C:\Users\`、家目录、`personal`、工作台目录名 |
| 凭据 | `sk-`、`gho_`、`ghp_`、`token`、`password`、`api-key`、`secret`、`.pem` |
| 运行时数据 | `state.json`、`sense-*`、`*history*`、`*.log`、`ledger`、`cookie` |
| 私人事务 | 健康、财务、副业、关系、作息（**这些最容易藏在配置里**） |

### 命令（Windows / PowerShell 可直接用）

```powershell
# 1) 已跟踪文件里的敏感文件名
git ls-files | Select-String -Pattern '\.env|token|secret|password|credential|\.pem|\.key$|state\.json|sense-|\.log$|cookie'

# 2) 全仓库内容扫描（含真名、学校、路径）
Get-ChildItem -Recurse -File |
  Select-String -Pattern '真名|学校|单位|年级|D:\\|C:\\Users\\|sk-|gho_' |
  ForEach-Object { "$([IO.Path]::GetFileName($_.Path)):$($_.LineNumber): $($_.Line.Trim())" }

# 3) 历史里出现过的文件（被删掉不代表没公开过）
git log --all --pretty=format: --name-only | Sort-Object -Unique |
  Select-String -Pattern '\.env|token|password|state\.json|personal'

# 4) 提交信息本身
git log --all --oneline
```

> **第 4 条最容易被忽略**：提交信息也是公开内容。有人在 commit message 里写了具体副业与生活安排，**代码干净但历史泄露**。

## 四、五个真实陷阱

**① `.gitignore` 救不了已经提交过的东西。**
文件的每一次提交都在历史里。转公开的一瞬间，历史一起公开。补救只有两条路：`git filter-repo` 重写历史（旧哈希全变、不可逆、需本人确认），或者**另起一个无历史的干净仓库**。**推荐后者**——干净、便宜、可验证。

**② `.gitignore` 不支持行尾注释。**
```gitignore
webview2-data/          # WebView2 用户目录，44MB
```
这一整行（含注释文字）会被当成**字面量模式**，规则**静默失效**——不报错，只是不生效。注释必须单独占一行。这是个不会报错、只会悄悄失手的坑。

**③ 绝对路径泄露用户名和目录结构。**
`C:\Users\张三\...`、`D:\work\personal\...` 这类字符串本身就在透露信息。改用环境变量或相对路径（例：`process.env.LIVELY_EXE || <常见位置>`、脚本用自身位置推导路径）。

**④ 运行时状态文件长得像"配置"，其实最私密。**
`state.json` 这种名字让人以为无害，实际里面是：真名、人格自评分、私人待办、每周自省答案。
**对策**：不入库 + 另发一个 `state.example.json` 模板，README 写「复制成 `state.json` 使用」。

**⑤ 编码/行尾在 Windows 上是真坑。**
- 中文 `.bat` 的编码**由代码页决定，先量再定**：`chcp` 是 `65001` → UTF-8；是 `936` → GBK。
  ⚠️ 这条与直觉相反，验收实测在一台 `chcp=65001` 的机器上 **UTF-8 成功、GBK 反而报"找不到路径"**，
  而在默认 GBK 的机器上正好相反。**最稳的做法是 bat 只用 ASCII**，中文路径换成 ASCII 启动器。
- **数据文件（`.json` 等）必须无 BOM**：PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会写 BOM，
  Node 的 `JSON.parse` 遇到 BOM 直接抛错。用
  `[System.IO.File]::WriteAllText($p, $json, (New-Object System.Text.UTF8Encoding($false)))`。
  **规则要分开：脚本带 BOM 是给 PS 自己读的；数据文件绝不能带 BOM。**
- PowerShell 脚本**要么带 BOM、要么别写中文**（PS 5.1 会把无 BOM 的 UTF-8 当 ANSI 读，
  中文注释能把语法读坏——本项目实测炸过一次）。**骨架全部用 ASCII，是更省事的选择。**
- 加一份 `.gitattributes` 锁行尾，`.bat`/`.ps1`/`.vbs` 保持 CRLF。

## 五、第三步：建干净仓库（推荐路线）

```
1. 确定最小文件集（源码 + 文档 + 结构，不含素材与运行时数据）
2. 新目录（与原仓库平级，不与原仓库嵌套）
3. 逐文件复制 → 排除 B 类与 C 类
4. 脱敏：替换真名/学校/路径/渠道名/提示词常量
5. 用 state.example.json 之类的模板替代运行时数据
6. 加 .gitignore（含运行时文件）+ .gitattributes（行尾）
7. 本地 git init → commit → 全量扫描 → 通过才建远端
8. 原仓库保持私有不动
```

**顺序很重要**：**先扫描通过，再建远端**。远端一旦建好，索引与缓存可能让内容留痕。

## 六、推不上去的时候（受限网络）

`git push` 可能三条路同时断（本项目实测）：直连被重置（`curl 56 Recv failure`）、SSH 因沙箱/策略无法创建命名管道、代理进程已不在。

**可用替代：GitHub 的 Git Data API（走 `gh`，它的网络通常是通的）**

```powershell
# 坑：空仓库上 POST /git/blobs 会返回 409 "Git Repository is empty"
# 解法：先用 Contents API 落一个初始提交（放 .gitignore，本来就是仓库要的文件）
gh api --method PUT "/repos/$owner/$repo/contents/.gitignore" --input seed.json --jq ".commit.sha"

# 然后 blobs → tree → commit（带 parent）→ 移动分支
gh api --method POST "/repos/$owner/$repo/git/blobs"    --input blob.json   --jq ".sha"
gh api --method POST "/repos/$owner/$repo/git/trees"    --input tree.json   --jq ".sha"
gh api --method POST "/repos/$owner/$repo/git/commits"  --input commit.json --jq ".sha"
gh api --method PATCH "/repos/$owner/$repo/git/refs/heads/main" -f "sha=$commitSha"
```
注意：blob 内容要按**原始字节**做 base64（`[IO.File]::ReadAllBytes` + `ToBase64String`），不要先解码成字符串再编码——否则 GBK 的 `.bat` 会被写坏。

## 七、第四步：发布后必须验证

**验证的是远端内容，不是你本地的副本。**

```powershell
# 从远端拉回关键文件再扫一遍
gh api -H "Accept: application/vnd.github.raw" "/repos/$owner/$repo/contents/README.md" > remote-README.md
# 然后对拉回来的文件跑第三节的扫描命令
```

- [ ] 远端文件清单里没有 `state.json` / 运行日志 / 素材图片
- [ ] 远端内容扫描无真名、学校、单位、路径、凭据
- [ ] 原仓库的可见性**没有被误改**
- [ ] `state.example.json` 之类的模板已就位，新用户能跑起来

## 八、别忘了 LICENSE

**没有 LICENSE 的公开仓库 = 保留所有权利**，别人**不能合法**使用、修改、分发。想让别人真的用得上，就得挑一个（MIT / Apache-2.0 最常见）。这一步很多人漏，等于白公开。

## 九、验收清单

- [ ] 三类内容已分类，A 类范围经本人逐项确认
- [ ] 已跟踪文件、全仓库内容、历史文件、提交信息 **四处都扫过**
- [ ] 运行时数据文件不入库，且有模板替代
- [ ] 绝对路径已改为环境变量或相对路径
- [ ] 第三方素材未打包，README 说明了「素材自备」
- [ ] `.gitignore`（含运行时文件）+ `.gitattributes` 就位
- [ ] **先扫描通过，后建远端**
- [ ] 发布后从**远端**拉回内容复扫一遍
- [ ] 原仓库未被误改
- [ ] LICENSE 已决定
