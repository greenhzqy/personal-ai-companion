# 验证纪律（贯穿全程）：怎么知道「真的修好了」

> 这一节是整套流程里**最贵的一课**。
> 本项目 13 个版本阶段里，AI 有 **8 个以上的"假修复"**是在这一节被拦下来的：以为修了、其实没修；以为坏了、其实是正常的；以为通过了、其实探针在骗自己。

---

## 一、核心信念

**「我改完了」不是证据，「我测到了」才是。**

每个「修好了」的背后，必须至少有一件：**探针输出 / 日志 / 截图 / 数值对比 / 真机现象**。
拿不出来的，一律写作「**未验证**」，而不是「应该好了」。

> 配套的一句：**先定位，不猜。** 本项目有一次用户说"并没有该处效果"，AI 以为是参数太小、加大一档，还是 0；上探针后才发现**那个模块从头到尾一次都没执行过**。猜测导致了两轮无用功。

---

## 二、十二个测量陷阱（几乎人人会踩）

### 关于"数据是旧的"
**① 长轮询/订阅式通道的数据，是在"请求发起那一刻"采样的。**
空闲时挂着的请求，返回的是**十几秒前的快照**。本项目因此连续得出两个**都是假的**结论（「rAF 坏了」「参数没生效」）。
> **修法**：关键量**锁存峰值**（`fpsMax` 这类），之后任何时候读都知道"曾经跑到多少"。别把瞬时快照当现状。

**② 会漂移的基准量不能只采一次。**
刷新率这种量在窗口遮挡/恢复切换时会剧烈变化。**锁存一次**会锁到坏样本（本项目锁到 13.1ms → 76Hz，导致所有分频算错）。
> **修法**：每秒重估（排一次中位数），成本可忽略。

### 关于"被测对象根本不在跑"
**③ 先确认屏幕上到底有什么，再解释数据。**
窗口被遮挡时 `requestAnimationFrame` **本来就不跑**——那是**正确行为**，不是 bug。本项目测了一个被遮得严严实实的窗口，得出"rAF 死了"，还据此加了三个强制渲染标志（**全是负优化，后来全部撤销**）。
> **修法**：先截屏/抓真实桌面看一眼。**这一步能省掉几小时的错误推理。**

**④ 测试环境的调度语义可能和生产完全不同。**
无头浏览器的 rAF 实测被节流到约 **0.7fps**——逐帧物理在那里**根本无法验证**。
> **修法**：先确认测试环境的时钟/调度行为，否则你测的是环境不是代码。

### 关于"读了但读错了"
**⑤ 带 transition 的元素，改完立刻读 `getComputedStyle` 读到的是过渡起点。**
规则明明生效，读出来是 `opacity=0`，差点去改一个没坏的 CSS。
> **修法**：测量前 `el.style.transition = "none"`。

**⑥ 静态单帧不能判断动画。**
面板截图里宠物被"压扁"，以为坏了——多帧探针证明那是教科书式的挤压拉伸。
> **修法**：**<300ms 的瞬时状态必须用时间序列采样验证**（注入探针连打几帧）。本项目另一次是键盘探针显示"某键不亮"，实际是点亮只维持 150ms 而截图正好抓在熄灭间隙。

**⑦ 坐标写死必然失败。**
被测元素是**底边锚定**的，视口高度一变它的 y 就变。
> **修法**：用元素实际几何（`getBoundingClientRect` / `elementFromPoint`）定位，**不要硬编码坐标**。

### 关于"探针自己在骗你"（最关键，最容易忽略）
**⑧ 探针输出必须逐条独立赋值。**
用长表达式链写探针，会被运算符优先级吞掉——本项目一个无障碍探针输出 `true`，**而那其实是 `aria-hidden` 的值**，不是"验证通过"。
> **修法**：每个观测量单独赋值、单独打印，输出要能**自证读的是谁**。

**⑨ 探针绕过逻辑路径 → "看起来通过"。**
探针直接调底层函数，就绕过了出 bug 的那段分支。
> **修法**：**把纯函数抄出来直接跑**（本项目一次跑 15 个用例，三个文案 bug 一次全出来）。

**⑩ 断言失败时，先怀疑断言本身。**
两个经典假失败：① 元素**尺寸为 0**（文字是 hover 时才写进去的），`elementFromPoint` 命中了别人；② 目标有 **1200ms 去抖**，连续两次点击第二次被吞。

**⑪ 用命令行做判据时，必须排除查询者自身。**
`... CommandLine -match 目标名` 的查询语句里**也含目标名**——匹配到了自己，于是"杀掉旧进程成功"是假的，旧进程一直活着。
> **修法**：精确匹配特征（`-File ...目标.ps1`）+ 排除自身 PID。

**⑫ ★ 失败态与否定态返回同一个值 —— 最隐蔽的一类。**
这是从坑 ⑪ 的同一条路上长出来的，但更狠，**值得当独立铁律**：

```powershell
Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" -ErrorAction SilentlyContinue |
  Where-Object { $_.CommandLine -like "*_keywatch.ps1*" }
```
在这台机器上，`Get-CimInstance` 因为权限被拒 —— 但加了 `-ErrorAction SilentlyContinue` 之后
**它不报错，只返回空**。于是「查询失败」和「确实没有这个进程」**返回了同一个值**。
调用方无法区分这两件事，只能一律当成"没有" → **每轮都多起一个进程**。

> **判据：一个检查如果无法区分"失败"与"否定"，它就不能用来做存在性判断。**
> **修法**：换成不会这么失败的判据（例：PID 文件 + 核对进程名）。
> **自检问法**：把这个检查的返回值打印出来时，**我能凭输出说出它是"失败了"还是"没有"吗？**
> 说不出，就说明这个检查不可用作判据。
>
> 同类高发场景：WMI/CIM 查询、`tasklist`/`netstat` 被安全软件拦、权限不足的注册表读取、
> 静默 `catch {}` 的异常吞掉。**本项目在"检测进程是否存在"上同时踩过三个变种。**

## 三、验证工具箱（按场景选）

| 你要证明的 | 用什么手法 |
|---|---|
| **现象无法从外部观测** | **把内部状态落盘**：在脚本里埋逐步骤日志写文件，再一次性读出来。本项目靠这一招从"窗口一坨黑"直达根因，被称为该轮最大价值 |
| 眼睛/画面里到底有没有它 | **探针浮在被测对象上方，同图对照**（本项目排除法走了 7 步没命中，同图对照一击命中） |
| 数值型调整有没有真的变 | **像素/数值前后对比**：把"看起来差不多"变成可比较的数字（本项目才发现"只压底色几乎没变"） |
| 能不能点、点到谁 | **先 `elementFromPoint` 取顶层元素，再派发真实事件**；断言"点哪里进哪里" |
| 端到端链路是否打通 | **让新数据搭一个"已经确定会通"的通道回来**（本项目用按键高亮通道带出脚部坐标，一次证明整条链通） |
| 是否有错误/内存问题 | **运行时审计页**：拦截 `onerror` / `unhandledrejection` / `console.error`，统计帧率与内存，画到页面上再截图 |
| 配置真的生效了吗 | **按实际内容验证**：读注册表/计划任务的实际值，而不是"脚本执行成功了" |
| 宿主应用"点了没反应" | **按宿主自己的日志目录定位**，比对成功/失败两条流程的差异——不要在自家代码里瞎找 |
| 我的改动真的在运行吗 | **看进程的实际命令行**（本项目借此揪出"运行的是旧目录里的另一份副本"）。<br>⚠️ **受限机器上这条会失效**：`Get-CimInstance Win32_Process` 可能整体被拒。<br>**替代判据**（按可靠性排序）：<br>① 让进程启动时写 **PID 文件**（含它自己的路径），看文件内容；<br>② `Get-Process | Select-Object Id, Path`（拿不到命令行，但能拿到**可执行文件路径**，足够区分两份副本）；<br>③ `netstat -ano` 看端口**属主的 PID**，再和你的进程对照。<br>**注意**：如果判据本身会静默失败（见陷阱 ⑫），先解决那个问题再谈验证。 |
| 隐私承诺是否成立 | **对"承诺的副作用"取证**：连续操作后看那个文件**字节数是否纹丝不动** |
| 纯逻辑对不对 | **把纯函数抄出来跑一批用例**（脱离宿主环境） |
| 降级路径是否真的能兜底 | **模拟失败**（关掉依赖，看兜底是否挂上、有无报错） |
| 定义/模板有没有写坏 | **独立静态解析**（不启动宿主，直接解析那份定义，检查元素是否齐全） |

### 一个特别值得学的组合：**静态审计 + 运行时审计**
本项目用"静态扫描找死代码与隐患 → 运行时审计看错误/帧率/内存 → 逐项修 → 复验"，一轮清掉 8 项隐患（包括删掉一个 670KB 的未引用文件、修掉两处负 delta 隐患、把过密的任务周期放宽）。**这套组合拳建议固定下来，每个阶段收口都跑一次。**

## 四、验证工具本身也要先验证

> **别假设你的测量工具是可靠的。**

本项目在同一个截图工具上留下了**三种互相矛盾的说法**（"视口固定 512px" / "width 参数有效" / "实际视口比请求值小 22×98"），还因此白改了两轮 CSS。
**修法**：加一条探针打印 `innerWidth`，**现场实测**，并且判断**只用相对量**（离底边多少），不要直接套绝对像素。

> 这条可以推广成一句原则：**文档化的工具能力也会随版本变化，能力边界要现场测。**

## 五、数值类 bug 的证伪法（值得单列）

**症状**：某个元素"时有时无"，像渲染随机丢失（连拍三帧：一帧都在、一帧只露一半、一帧全无）。

**根因**：`dt` 只封了**上限**没封下限。而帧回调收到的时间戳**可能早于**驱动它的时钟源 → `dt` 为负 → 插值系数变成负数且绝对值 > 1 → **指数发散**，元素被推到画面外（NDC 坐标飞出 `[-17.7, -11.0]`）。

**可迁移的铁律**：
- **插值系数必须钳位到 `[0,1]`**；
- **`dt` 必须同时封上下限**；
- **时钟源只能有一个**——混用两个时钟必然出现负 delta（本项目两处都栽在这上面）。

> 这类 bug 用"看代码"几乎找不出来，**必须靠探针把中间量打出来**。

## 六、验收

- [ ] 每个结论都附了证据（探针/日志/截图/数值），没有"应该好了"
- [ ] 涉及**瞬时状态**的验证用了时间序列，不是单帧
- [ ] 涉及**数值调整**的验证做了前后对比，不是肉眼"差不多"
- [ ] 探针输出**逐条独立**，能自证读的是谁
- [ ] 改了代码后确认过**进程实际命令行**指向的是这份代码
- [ ] 阶段收口时跑过一次**静态 + 运行时**双向审计
- [ ] 拿不到证据的项，明确标了「**未验证**」而不是"通过"

---

## 七、把这条纪律变成习惯的三句话

1. **先定位，不猜。** 加大参数之前先问"它到底执行了没有"。
2. **先确认被测对象在跑，再解释它的数据。**
3. **探针也会错，验证脚本要像代码一样被审查。**
