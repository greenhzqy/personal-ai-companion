# 阶段 5 · 工程化与护屏：让它挂了你也能修，长期开着也不伤机器

> 只在两种情况下需要这一阶段：**你要长期挂着它**，或者**它跑在一台你不在跟前的机器上**。
> 如果只是自己笔记本上偶尔看看，可以跳过——但别跳过"它崩了你怎么知道"这个问题。

---

## 一、自愈看门狗：没人看着的机器必须能自己爬起来

**问题**：机器放在工位/宿舍长期开机，用平板远程。任何一环悄悄死掉，都要等**有人凑巧去看**才发现。

**做法**：一个定时任务，每 10 分钟检查一遍，缺哪个补哪个。

```
每 10 分钟：
  1) 本地服务端口在听吗？        不在 → 拉起来（起完再验一次，见下）
  2) 键盘监听进程在吗？            不在 → 拉起来（用 PID 文件判定，见坑 ①）
  3) 壁纸引擎在吗？                不在 → 拉起来
  4) 日志超过 N 行 → 截断（别让它无限长）
```

> **可直接用的实现见 `scripts/_watchdog.ps1` + `_watchdog.vbs`**（含端口探测用原始 TCP 而不是
> `Get-NetTCPConnection`、PID 文件判定、起完复验、日志截断，全部实测过）。
> 下面是每一步的**关键约束**，照着写才不会踩坑：
>
> | 步骤 | 关键约束 |
> |---|---|
> | 1 端口在听吗 | **不要用 `Get-NetTCPConnection`**——权限不足时它静默返回空（见坑 ①的同类）。用 .NET `TcpClient.BeginConnect` + 超时，几百毫秒就能判定 |
> | 1 拉起来之后 | **必须复验**：等几百毫秒再探一次端口。否则文件缺失/语法错/端口被占时，日志会永远写"已重启"，而服务根本没起来——**一个说谎的看门狗比没有更糟**。起不来就写 `start FAILED` |
> | 2 进程在吗 | 用 **PID 文件 + `Get-Process -Id`**，并核对进程名（防 PID 回收复用）。**不要用 WMI** |
> | 3 引擎在吗 | 按进程名判断（这一步 `Get-Process -Name` 就够了）。路径拿不到就跳过并记日志，**不要瞎猜路径** |
> | 4 日志截断 | 超过 N 行只保留最后 M 行。**只在需要动作时才写日志**——这样"日志很安静"本身就是一个健康信号 |

### 五个真实的坑

**① 判断「进程在不在」：两个直觉写法都会静默出错。**

**写法 A —— 按进程名（永远为真）：**
```bat
tasklist /fi "IMAGENAME eq powershell.exe" | findstr /i "powershell"
```
这个判断**永远成立**——因为 bat 自己就 spawn 了一个 powershell。后果：**每次登录都多起一个监听进程**，实测累积了 3 个。

**写法 B —— 按命令行匹配（在受限机器上整体不可用）：**
```powershell
Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" |
  Where-Object { $_.CommandLine -like "*_keywatch.ps1*" }
```
**验收实测：在受限环境里 `Get-CimInstance` / `Get-WmiObject` / `Get-NetTCPConnection` / `tasklist`
全部返回 Access denied。** 更糟的是——**加上 `-ErrorAction SilentlyContinue` 之后它不报错，只返回空**。
于是"进程在不在"这个问题的**失败态与否定态返回了同一个值**，看门狗每轮都以为该进程不在，
**每轮多起一个**，正是写法 A 那个事故的翻版（而且更隐蔽，因为你以为已经修好了）。

> **修法：用 PID 文件，不要依赖任何特权接口。**
> 让被监控的进程启动时把自己的 PID 写进一个文件（就放在脚本旁边），
> 看门狗读那个文件 + `Get-Process -Id` 确认它还活着（并核对进程名，防止 PID 被回收复用）。
> - 不需要任何权限，不会静默失败；
> - 它天然只能指向**本目录**的进程，不会误杀别人机器上同名的脚本；
> - 文件里的 PID 已经死了 → 判定为陈旧，删掉文件重新拉起。
>
> 完整实现见 `scripts/_watchdog.ps1`（实测四种情形：起 / 不重复起 / 陈旧 PID 重起 / 起不来时如实报 FAILED）。
>
> **WMI 那套只在"清理历史遗留的重复进程"时当尽力而为的补充**：拿不到就静默跳过，**绝不能让检测主路径依赖它**。注意在 WMI 受限的机器上，这一步会**永远匹配 0** —— 也就是"重复清理"这条验收在那类机器上并没有真正生效过，别把它当成已验证。

**② 计划任务直接跑 `powershell.exe` 会每 10 分钟闪一次黑框。**
> **修法**：用 `wscript` 起，`Run "powershell.exe ...", 0, False`——第二参数 0 = 隐藏窗口。

**③ 脚本里不要写死本机绝对路径。**
`_watchdog.vbs` 这类脚本应当**从自身位置推导目录**：
```vbs
Set fso = CreateObject("Scripting.FileSystemObject")
here = fso.GetParentFolderName(WScript.ScriptFullName)
```
程序路径（node、壁纸引擎）优先走 PATH 与常见安装位置，允许用环境变量覆盖。**既为了可移植，也为了不泄露你的目录结构**（见发布那一节）。
> ⚠️ **"常见安装位置"经常猜不中**（验收实测：三个猜测路径全落空，而机器上其实装了）。
> **别猜——去问系统**：从正在运行的进程拿它的可执行文件路径
> （`Get-Process <名字> | Select-Object -ExpandProperty Path`），或者从启动项/快捷方式里读出实际路径。
> 拿到之后写进环境变量覆盖位，比列一堆猜测路径可靠。

**④ 常驻进程不能靠"随手启动"，要交给系统调度器托管。**
用工具/脚本 `Start-Process` 起的进程**不保证比调用活得久**——它可能被回收（Windows 上是 Job Object），表现为「检查的时候还活着，下一次调用就没了」。本项目的一句话记录：「服务器只是个残留进程，重启就没了」。
> **修法**：需要长期存活的进程，用**计划任务**（或同等的系统级调度器）注册，而不是让某个脚本 spawn 它。

## 二、性能闸门：不可见时一帧都不跑

**目标不是"高帧率"，是"该跑的时候跑得好，不该跑的时候彻底停"。**

### 核心设计

| 设计 | 为什么 |
|---|---|
| **可见性驱动** | 页面隐藏时直接**不进函数体**（连 `setInterval` 的回调都拦掉），而不是"跑了但不画" |
| **整数分频，不用时间容差** | 用「距上帧 ≥ 1000/60 − 1.5ms」这种容差，实际间隔会在 12/18ms 之间跳，**平均 55fps 但看起来是顿的**。改成先量出真实刷新率，再取整分频（每 N 个刷新帧放行一次），**每个放行帧间隔严格相等** |
| **每秒重估，不要锁存** | 锁存会在窗口遮挡/恢复切换时锁到坏样本（实测锁到 13.1ms → 76Hz），导致分频全算错 |
| **活跃度分级** | active / idle / away 三档，帧率阶梯下降（例：原生 → 40 → 15），而不是二值开关 |
| **电池感知** | 用电池时连 active 也降下来 |

> **观感上，均匀的帧间隔比高帧率更重要。** 这一条是本项目最贵的性能结论。

**可用的最小实现**（这段是能直接放进页面的，不是示意）：

```js
/* 帧闸门：先量真实刷新率，再按目标帧率取整分频。
   两条约束必须同时满足，否则会出反模式：
     ① 不可见时一帧都不给（不是"跑了但不画"）
     ② 同一帧内所有回调共享一个决定（不能各自判断，否则后面的循环被饿死） */
(function () {
  var TARGET = { active: 0, idle: 40, away: 15 };   // 0 = 原生，能跑多快跑多快
  var vsync = 16.7, div = 1, level = "active";
  var tick = 0, lastTs = -1, countAt = 0, frames = 0, gaps = [];

  var _raf = window.requestAnimationFrame.bind(window);
  window.requestAnimationFrame = function (cb) {
    return _raf(function (t) {
      if (document.hidden) { window.requestAnimationFrame(cb); return; }   // ①

      if (t !== lastTs) {                      // 新时间戳 = 一个新刷新帧
        if (lastTs >= 0) {
          var gap = t - lastTs;                // 只收合理区间，避开切窗口的坏样本
          if (gap > 2 && gap < 200) { gaps.push(gap); if (gaps.length > 120) gaps.shift(); }
        }
        lastTs = t; tick++; frames++;
        if (!countAt) countAt = t;
        if (t - countAt >= 1000) {             // 每秒重估一次
          if (gaps.length >= 20) {
            var s = gaps.slice().sort(function (a, b) { return a - b; });
            vsync = s[s.length >> 1];          // 中位数，抗抖
            var tgt = TARGET[level];
            div = tgt > 0 ? Math.max(2, Math.round((1000 / vsync) / tgt)) : 1;
          }
          frames = 0; countAt = t;
        }
      }

      if (div > 1 && (tick % div) !== 0) { window.requestAnimationFrame(cb); return; }  // ②
      cb(t);
    });
  };

  // 档位由你的活动判据驱动（见阶段 4 的"表现轴"阈值）
  setInterval(function () {
    var idle = /* 你自己的空闲秒数来源 */ 0;
    level = idle < 15 ? "active" : (idle < 150 ? "idle" : "away");
  }, 1000);
})();
```

> **配一条自检**：探针统计**每个** rAF 循环的执行次数。只盯主循环，就看不出"后面的循环被饿死"（那个 bug 的表现是某个循环的执行次数**恰好为 0**）。

> ⚠️ **反模式：不要为了"让它继续跑"而加强制渲染标志**（如 Chromium 的 `--disable-features=CalculateNativeWinOcclusion`）。
> 那会强迫引擎渲染看不见的窗口，纯浪费 GPU、增热、费电——**和护屏完全相反**。本项目加过一次，全部撤销。

### 固定频率任务的周期怎么定：按"最坏可接受延迟"反推

不要抄一个常见数字。**先写下这个任务最坏能忍受多慢，再反推周期。**

本项目的两个例子：
- 看门狗唤醒原本 **40ms**（每秒 25 次，明显过密）→ 放宽到 **110ms**，因为它的判定阈值本来就是 300ms，**110ms 完全兜得住**；
- 面板轮询状态从 **5 秒**放宽到 **12 秒**，因为界面上的数字本来就不需要 5 秒级新鲜度（而且每次要拉并全量重绘一个几 KB 的 JSON）。

> **通用原则：周期 = 由"最坏可接受延迟"反推的结果，不是习惯值。** 顺手把每个定时任务都过一遍，问一句「它真的需要这么快吗」。

### 取数成本：一次 spawn 半秒，必须算进账

**这是最容易被忽略的一条成本。** 验收实测：**每次 `spawn` PowerShell 实测 476–489ms**。
如果你让服务"每个请求都 spawn 一次"，那么缓存时间（TTL）就决定了这台机器的开销：

| 缓存 TTL | 每小时 spawn 次数 | 评价 |
|---|---|---|
| 1.5 秒 | ≈ 2400 次 | ❌ **和"护屏"目标直接冲突**（白烧 CPU、风扇、电） |
| 5 秒 | ≈ 720 次 | ⚠️ 可接受，但要和消费端的轮询周期对齐 |
| 长驻采样进程 | **1 次** | ✅ 推荐 |

**推荐架构：起一个长驻采样进程，而不是每个请求 spawn 一次。**

```
采样进程（长驻 PowerShell/Node）
   每 N 秒采一次 → 写 sense.json（无 BOM）
   ↓
本地服务       → 只读那个文件，不 spawn
   ↓
消费端         → 轮询 /sense
```

好处一次说清：
- **一次启动成本，之后是纯读文件**；
- 采样周期可以**跟着活跃度退避**：active 每 5 秒、idle 每 15 秒、away 每 60 秒——
  这正好和阶段 4 的三档状态机用同一套判据，**护屏和感知不再是两件事**；
- 采样进程的存活由看门狗用 **PID 文件**管（同一个模式，见上一节）；
- 顺带得到一个诊断量：**样本年龄**（现在这份 JSON 是几秒前采的），
  消费端可以据此拒绝用过期数据（这正是阶段 6「别把十几秒前的快照当现状」的根治办法）。

> 骨架 `scripts/sense-server.js` 目前实现的是**带缓存的一次性 spawn**（简单、单文件、够用），
> 缓存 TTL 已按上表设为 5 秒。要 24 小时挂着，**建议改成长驻采样进程**——
> 验收员独立实现过这一版（`sampler.ps1` + PID 文件），并实测 `/sense` 返回里带 `sampleAgeMs`。

### 两个必须避开的反模式

**① 不要为了"让它继续跑"而加强制渲染标志**（如 Chromium 的 `--disable-features=CalculateNativeWinOcclusion`）。那会**强迫引擎渲染看不见的窗口**，纯浪费 GPU、增热、费电——**和护屏完全相反**。本项目加过一次，全部撤销。

**② 节流闸门必须是"共享的帧决策"，不能是"每个订阅者各自判断"。**
最直觉的写法是：
```js
window.requestAnimationFrame = function (cb) {
  return _raf(function (t) {
    if (t - lastFrame < minInterval) { window.requestAnimationFrame(cb); return; }  // ← 错
    cb(t);
  });
};
```
**后果**：一帧之内只有**第一个**回调能通过，其余全部被重新排队。谁的循环先注册谁就永远抢在前面——**后面的 rAF 循环（例：光照、动画）一次都跑不到**（本项目探针打出"执行次数 = 0"）。
> **正确做法**：闸门按**「帧」**决定而不是按「回调」——每个新的帧时间戳只判断一次，**同一帧内所有回调共享这个结论**。
> 验证方法：探针统计各循环的执行次数，不能只看主循环。

## 三、护屏：最大的杠杆在系统设置里，不在代码里

**先认识硬件**：
- **IPS 屏**怕的是**发热**和**背光时长**，不是烧屏（OLED 才主要怕烧屏）；
- 一块笔记本屏背光连续点亮几个月，是整机寿命最短的部件之一。

**所以最大的杠杆是系统电源设置**：

| 项 | 建议 | 理由 |
|---|---|---|
| 显示器超时（交流） | **改短**（例 30 分钟） | 关屏后合成器停止工作 → 渲染自然归零，**比任何代码优化都彻底** |
| 睡眠 | **长期远程的机器不要改成睡眠** | 一旦睡下去，远程可能够不到 → 失联 |
| 电池充电上限 | 长期插电开到 60%/80% | 长期满电最伤电池 |

> **为什么关屏不会让你失联**：远程输入走的是标准输入栈，会重置空闲计时器 → 屏幕立刻亮。只要你还在操作，屏幕就是亮的。

**代码端再补四件套**（都是锦上添花，别本末倒置）：
1. **降帧**（上节的活跃度分级）
2. **压暗**：一个覆盖层，idle 轻微、away 明显
3. **停 CSS 动画**：静止帧可被合成器复用，几乎不耗 GPU
4. **像素漂移**：静态文字（落款、日期）每几分钟挪几像素

## 四、Windows 上的编码与脚本坑（血泪）

> ⚠️ **先说一条元规则：编码规则是"看环境"的，凡是写成绝对命令的都值得怀疑。**
> 下面每一条都给**判定方法**，不要照抄结论。

| 现象 | 根因 | 修法 |
|---|---|---|
| 中文台词/菜单全乱码 | PowerShell 5.1 把**无 BOM 的 UTF-8** 当 ANSI/GBK 读 | `.ps1` 存成 **UTF-8 with BOM**；**或者干脆脚本里不写中文**（骨架全部用 ASCII，最省事） |
| `.bat` 里含中文路径 → 自启指向不存在的文件 | cmd 按**当前代码页**解释 bat 的字节 | **先量再定**：`chcp` 看代码页。<br>`65001` → **UTF-8** 的 bat；`936` → **GBK** 的 bat。<br>⚠️ **这条与直觉相反**：验收实测在一台 `chcp=65001` 的机器上，**UTF-8 成功、GBK 反而报"找不到路径"**；而在默认 GBK 的机器上则相反。**别照抄任何一边，先跑 `chcp`。**<br>最稳的做法：**bat 只用 ASCII，中文路径一律换成 ASCII 启动器**，从根上绕开。 |
| **Node 读 JSON 抛 `JSON.parse` 错** | PowerShell 的 `Set-Content -Encoding UTF8` 在 5.1 下**会写 BOM**，而 JSON 标准不允许 BOM | **数据文件必须无 BOM**：用<br>`[System.IO.File]::WriteAllText($path, $json, (New-Object System.Text.UTF8Encoding($false)))`<br>**规则区分开：脚本（`.ps1`）带 BOM 是为了 PS 自己读得对；数据文件（`.json`）绝不能带 BOM。** |
| 抓不到子进程输出 / 命令莫名失败 | 受限环境下**管道 stdio 被禁止**（`spawn`/`execFile`/`exec` 默认或 `'pipe'` 会抛 `EPERM`） | 只有一种组合能活：**`stdio: 'ignore'` + 让子进程自己把结果写进文件**，父进程读文件。<br>⚠️ 两个常见的错误替代：`'inherit'` **读不回值**（只落在控制台）；`'ignore'` 而不让子进程写文件 = **静默无输出**。<br>实测：6 种变体只有这 1 种能活。 |
| 用 `Get-CimInstance` / `tasklist` 判断进程 → 每轮多起一个 | WMI/工具被拒时**静默返回空**，失败态与否定态同值 | 见上一节坑 ①：改用 **PID 文件** |
| `.gitignore` 规则不生效 | 写了**行尾注释**（不支持），整行被当字面量 | 注释**单独占一行** |

## 五、产出物与验收

- [ ] 手动杀掉本地服务，**10 分钟内它自己回来**
      > **受限环境的降级测法**：如果不能等 10 分钟（或不能改计划任务周期），
      > 就**手动跑一次看门狗**并把间隔参数调小来测逻辑——但要如实记下
      > 「验的是逻辑，不是真实的 600 秒周期」。验收员 B 做的是真标准：
      > **杀进程 → 等到下一个周期 → 记录停机时长**（实测停机 10 分 02 秒）。
- [ ] 杀两次，**不会出现两个监听进程**
      > ⚠️ 在 WMI 受限的机器上，**"清理重复"这一步永远匹配 0（静默空转）**——
      > 那种环境下这条**没有被真正验证**。真正在起作用的是 **PID 文件判定**，
      > 所以验收要盯的是"有没有多起"，而不是"清理动作有没有跑"。
- [ ] 连续挂 24 小时，**没有可见的性能影响**（该停的时候真停了）
      > 附带对账：**每次 spawn 约 0.5 秒**，按你的缓存 TTL 算一下每小时多少次（见"取数成本"）。
- [ ] 关屏后 GPU 占用**归零**（不是"降低"）
      > **必须有测量方法，否则这条写不进验收**。Windows 上可用性能计数器：
      > ```powershell
      > Get-Counter '\GPU Engine(*engtype_3D)\Utilization Percentage' |
      >   Select-Object -ExpandProperty CounterSamples |
      >   Where-Object { $_.CookedValue -gt 0 } | Select-Object InstanceName, CookedValue
      > ```
      > 关屏前后各采几次对照。**注意**：不是所有驱动都暴露这组计数器——
      > 拿不到时降级为"壁纸进程的 CPU 占用趋近 0 + 该进程的渲染线程不再唤醒"，
      > 并**在记录里写明用的是降级判据**，不要含糊成"已归零"。
